# Solace Bay Resort & Spa — Full-Stack Booking Platform

A production-oriented hotel booking website: a public site for browsing rooms and booking stays, and
an admin panel for running the hotel day-to-day (including manually entering phone/walk-in bookings).

Stack: **Next.js 14 (App Router) + TypeScript + Tailwind CSS**, **PostgreSQL + Prisma**, **NextAuth**
(credentials + JWT), **Razorpay**, **Cloudinary** (image upload — see note below), **Resend** (email).

See `ARCHITECTURE.md` for the full architecture, ER schema, page/API list, roles, booking flow, admin
workflow, and phased roadmap this project was built against.

---

## ⚠️ Before you run this

Every file in this project was hand-written directly rather than generated by `create-next-app` /
`npm install`, because **the sandbox this was built in has no access to the npm registry** (outbound
requests to `registry.npmjs.org` and mirrors are blocked at the network level — this is an environment
restriction, not a project issue). That means:

- None of the code here has been run, compiled, or type-checked yet.
- You need to run `npm install` yourself, on your own machine, where npm access is normal.
- The Prisma schema has not been migrated against a real database yet — you'll run that too.

The code was written carefully against the exact API shapes of each pinned dependency version, so it
should install and run cleanly — but treat the first `npm run dev` and `npx prisma migrate dev` as the
real first test of this codebase, and expect to fix a small type error or two if a dependency's API
shifted slightly from what's pinned in `package.json`.

## 1. Prerequisites

- Node.js 18.18+ and npm
- A PostgreSQL database (local Postgres, or a hosted one — Neon, Supabase, Railway, RDS, etc.)
- A [Razorpay](https://razorpay.com) account (test mode is fine) for payments
- A [Cloudinary](https://cloudinary.com) account for image hosting (optional for local dev — the site
  renders elegant gradient placeholders everywhere until real images are added, see below)
- A [Resend](https://resend.com) account for transactional email (optional for local dev)

## 2. Install

```bash
cd solace-bay-resort
npm install
```

## 3. Configure environment variables

```bash
cp .env.example .env
```

Then fill in `.env`:

| Variable | Notes |
|---|---|
| `DATABASE_URL` | Postgres connection string |
| `NEXTAUTH_URL` | `http://localhost:3000` for local dev |
| `NEXTAUTH_SECRET` | Generate with `openssl rand -base64 32` |
| `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` | From your Razorpay dashboard (test mode keys work) |
| `NEXT_PUBLIC_RAZORPAY_KEY_ID` | Same as `RAZORPAY_KEY_ID` — exposed to the browser checkout widget |
| `CLOUDINARY_*` | Only needed once you start uploading real photos |
| `RESEND_API_KEY` / `EMAIL_FROM` | Only needed for booking confirmation emails |
| `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` | The admin login the seed script creates |

## 4. Set up the database

```bash
npm run prisma:migrate   # creates all tables from prisma/schema.prisma
npm run prisma:seed      # populates the hotel, 5 room types, pricing, a coupon, sample reviews, etc.
```

The seed script prints the admin and staff login credentials it creates. By default:

- **Admin:** `admin@solacebayresort.com` / `ChangeMe123!` (or whatever you set in `.env`)
- **Staff:** `frontdesk@solacebayresort.com` / `FrontDesk123!`
- **Sample guest accounts:** `priya.mehta@example.com`, `rohan.deshpande@example.com`,
  `kavita.kulkarni@example.com` — all password `Guest1234!`

**Change the admin password** (or delete/recreate the seeded admin user) before this goes anywhere
near a real environment.

## 5. Run it

```bash
npm run dev
```

Visit `http://localhost:3000` for the public site and `http://localhost:3000/admin` for the admin
panel (log in with the admin credentials above first — `/admin` redirects to `/login` otherwise).

## 6. Optional: Razorpay webhook (local testing)

The booking flow verifies payments client-side (`/api/payments/verify`), but `/api/webhooks/razorpay`
is a server-to-server fallback for cases where the client never gets to call verify (closed tab, etc.).
To test it locally, use the Razorpay CLI or `ngrok` to forward Razorpay's webhook to
`http://localhost:3000/api/webhooks/razorpay`, and set the same secret in your Razorpay dashboard and
`RAZORPAY_KEY_SECRET`.

## Images: the placeholder system

There is no real photography for this project yet, so every image slot — hero, room cards, gallery,
service cards — renders `<PlaceholderImage />` (`src/components/site/placeholder-image.tsx`): a
deliberately designed gradient block, not a broken `<img>` tag. This keeps the site looking premium
and complete with zero real assets.

To switch to real photos once you have them:

1. Upload images to Cloudinary (a small admin upload flow is a natural next addition — wire it to
   `CLOUDINARY_*` in `.env` — or upload directly via the Cloudinary dashboard/API for now).
2. Store the resulting URLs in `RoomImage.url`, `GalleryImage.url`, `ServiceImage.url`.
3. Swap `<PlaceholderImage seed={n} />` for `<Image src={url} ... />` at each call site. Every call
   site reads from the same field shape, so this is a mechanical swap, not a redesign.

## What's implemented

- **Public site:** Home, Rooms catalogue with live availability search, Room Details with a booking
  panel, guest review + coupon flow, Razorpay checkout, booking confirmation, customer account/booking
  history, cancellation with policy-based refund calculation, Contact, Gallery, Services, Offers.
- **Admin panel:** KPI dashboard with a revenue chart, Room Management, full Booking Management
  (search/filter, confirm/cancel/complete/no-show, mark payments paid) **including creating
  offline/phone/walk-in bookings that immediately reduce live availability**, a visual availability
  Calendar, Pricing rule management (weekend/seasonal/holiday), Coupons, Reviews (approval workflow),
  Contact message inbox, and hotel-wide Settings (name, address, policies, taxes, social links) — all
  editable without touching code.
- **Security:** bcrypt-hashed passwords, JWT sessions, server-side RBAC (`assertRole`) on every admin
  mutation and API route plus edge-level middleware on `/admin/*`, Zod validation on all inputs,
  HMAC-verified Razorpay payments, secrets isolated to environment variables.
- **Booking-overlap correctness:** availability is always computed live (never a stored counter) from
  overlapping `PENDING`/`CONFIRMED` bookings plus any physical rooms under maintenance, and booking
  creation runs inside a `Serializable` database transaction so two simultaneous bookings can never
  double-book the last room.

## What's stubbed / next steps

- **Photography** — see above.
- **Transactional email** — the `Notification` table records every event (confirmations,
  cancellations, new bookings); wiring `resend`/`@react-email/components` to actually send on those
  events is a small, isolated addition (`src/server/services/*` already call `db.notification.create`
  at every relevant point — a notification dispatcher can hook in there).
- **Amenities / Gallery / Restaurant content management UI** — the `Amenity`, `GalleryImage`, and
  `Service` (services already have full CRUD potential via the same pattern as Rooms/Coupons) tables
  exist and are seeded; dedicated admin CRUD screens for Amenities and Gallery follow the exact same
  pattern as `/admin/rooms` or `/admin/coupons` if you want them added next.
- **n8n / webhook automation hooks** — not required for v1 per the spec; `N8N_WEBHOOK_URL` is reserved
  in `.env.example` for exactly this when it's time.
